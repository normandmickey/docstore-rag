Why Docstore exists

AI around documents usually breaks in one of two ways: either it stays trapped as a demo chat widget bolted onto uploads, or it gets spread across too many disconnected tools to trust. Docstore takes a different approach. The idea is simple: build one private system where documents can be ingested, organized, retrieved, synced, questioned, and delivered into the channels where people actually work.

A private knowledge layer Put uploads, URLs, synced folders, and extracted knowledge into one tenant-aware system instead of scattering them across separate tools.
Grounded answers, not loose summaries Retrieval is scoped to the current workspace so the system stays useful for actual policy, support, and operations questions.
One backend, multiple delivery channels Use the same knowledge base for dashboard chat, support workflows, Zoom Chat, Telegram, Discord, and voice.

Underlying technology and tools

The product story comes first, but the underlying stack matters because reliability, privacy, and delivery discipline matter. Docstore is intentionally built on boring, inspectable infrastructure where possible, with AI components used where they actually add value.

Core application layer Django drives the main product: auth, admin, dashboard, tenant/workspace control, connectors, reports, support views, and APIs.
Database and retrieval Postgres is the system of record, with pgvector for semantic search and retrieval across workspace documents.
Embeddings and generation OpenAI embeddings power semantic indexing, while Groq-hosted generation is used for cost-efficient chat and rewrite tasks.
Private storage Files and generated assets are kept in private MinIO-backed object storage rather than open public blob URLs.
Execution plane separation Chatbots and voice agents live in separate services so Django stays the control plane and channel execution stays modular.
Operational tooling Celery handles background work, scheduled connector syncs, and ingestion workflows, while systemd-backed services keep the app, workers, bots, and voice agents running cleanly.
Why this stack It keeps the product debuggable, deployable, and expandable. The goal is not maximum novelty. The goal is a system you can trust and grow.
What stays opinionated Django and Postgres remain the product brain. Execution services stay separate. Storage stays private. Retrieval stays workspace-scoped.

How the product is structured

1. Bring knowledge in Upload files, ingest URLs, or connect synced folders so documents enter the system in a trackable way.
2. Keep it tenant-aware Tenants, workspaces, permissions, API keys, and connectors define who can access what and where knowledge should be used.
3. Deliver it where it matters Use dashboard chat, support workflows, reports, bots, and voice agents as delivery surfaces on top of the same source material.
