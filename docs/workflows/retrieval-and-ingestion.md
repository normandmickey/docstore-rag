# Retrieval and Ingestion Workflow

This document describes the current docstore ingestion/retrieval workflow as of the latest OpenAI-embeddings + Groq-generation architecture.

## Goals

The current workflow is designed to:

- keep embeddings stable and high-quality
- use cheaper/faster generation where possible
- make retrieval inspectable, not mysterious
- improve exact policy/list lookup for handbook-style documents
- avoid paying LLM costs for obviously low-value chunks

## Provider split

### OpenAI
Used for:
- embeddings only

Current default:
- `text-embedding-3-large`

### Groq
Used for:
- chunk question generation
- question rewrite
- chat answer generation

Current model family:
- `openai/gpt-oss-20b`

## Ingestion workflow

### 1. File acquisition
A document enters via:
- dashboard upload
- URL ingestion
- future connector flows

### 2. Extraction
The production-safe default path is the standard extractor.

Currently supported:
- PDF via `PyMuPDF`
- DOCX via `python-docx`
- Markdown / TXT / HTML

### 3. Text normalization
Extracted text is normalized to reduce:
- line-break noise
- repeated blank lines
- some embedded glyph corruption
- low-signal numeric/leader-line junk

Note: glyph corruption is still an open problem for some PDFs.

### 4. Chunking
Docstore currently uses:
- `RecursiveCharacterTextSplitter`
- ~1000 char chunks
- ~20% overlap

After chunking, overlong chunks are split again to stay within safe embedding input size.

### 5. Chunk structure analysis
Each chunk is analyzed for lightweight structure signals such as:
- heading candidates
- dominant heading
- list presence
- list count
- line count

This feeds both metadata generation and extracted facts.

### 6. Metadata generation
Each chunk gets:
- `metadata_text`
- `question_text`

#### metadata_text
A retrieval-oriented description containing things like:
- document filename
- dominant heading (if trusted)
- chunk type
- list count
- keywords
- short summary

#### question_text
A retrieval-oriented set of likely user questions the chunk can answer.

Current behavior:
- heuristic first
- optional guarded cheap-LLM enhancement on high-value chunks
- if LLM returns good chunk-specific questions, those win over heuristic fallback

### 7. LLM question generation guardrails
LLM question generation is intentionally constrained.

Current rules:
- only for chunks above a minimum size
- only for chunks that appear semantically useful
- skip obvious TOC / noisy / corrupted chunks
- cap the total number of chunks per ingestion run that use LLM generation
- generate only 2 questions

This keeps cost under control and avoids wasting money on garbage chunks.

### 8. Embedding write
For each chunk, docstore writes embeddings for:
- raw chunk text
- metadata text
- question text

Embeddings use OpenAI.

### 9. Extracted facts
Docstore also creates heuristic `ExtractedFact` rows such as:
- `heading`
- `list_item`
- `policy`

These are currently useful for:
- inspection
- debugging
- supplemental retrieval/context

## Retrieval workflow

### 1. Rewrite question
Incoming user questions are rewritten into standalone form using Groq.

Goal:
- preserve meaning
- reduce follow-up ambiguity
- improve retrieval query quality

### 2. Candidate retrieval
Docstore retrieves candidates from multiple signals:
- raw chunk embedding similarity
- metadata embedding similarity
- question embedding similarity
- Postgres full-text lexical ranking

### 3. Blended ranking
Candidates are blended into a combined score.

The exact weights are still tunable, but the key point is:
- retrieval is no longer single-signal
- multiple representations of the same chunk compete together

### 4. Local expansion
After the best hit is identified, docstore also pulls nearby chunks from the same document region.

Goal:
- reduce isolated-chunk brittleness
- preserve section-local context

### 5. Optional fact context
The facts layer may also contribute context for some queries.

### 6. Answer generation
Chat answers are generated by Groq using only the provided retrieved context.

Prompt behavior is strict:
- use provided context only
- do not invent facts
- say you do not know if unsupported
- prefer bullet lists when context clearly contains list answers

## Inspection workflow

Docstore now exposes useful inspection surfaces.

### Per-document pages
- overview
- facts
- chunks
- search

### Chunk inspection shows
- metadata text
- question text
- raw chunk text

### Search inspection shows
- retrieval scores
- metadata text
- question text
- chunk text

This is now one of the most important debugging workflows in the product.

## Lessons learned so far

### 1. Extraction quality still matters a lot
If PDF extraction is dirty, retrieval gets poisoned downstream.

### 2. Metadata helps, but bad headings hurt
Aggressive heading inheritance created junk like executive names being treated as headings.
That is now filtered much more strictly.

### 3. Question embeddings are promising
Question-style retrieval text is often closer to how users actually ask.
This is especially useful for handbook/policy docs.

### 4. Cheap LLM generation needs guardrails
Unbounded generation would waste money on low-value chunks.
The current guarded approach is a deliberate compromise.

### 5. Docling is not ready for regular VPS use here
Docling was valuable as an experiment, but current runtime on this VPS is too slow for practical ingestion.
Keep it experimental for now.

## Current weak spots

These are the most important remaining weaknesses:

- glyph corruption in some PDFs
- near-miss ranking issues (correct topic, wrong chunk)
- some question-generation outputs still need to become more chunk-specific
- exact-list answers still need stronger precision

## Practical tuning guidance

If retrieval picks the wrong chunk:
1. inspect document-scoped search results
2. compare metadata text, question text, and chunk text
3. decide whether the problem is:
   - extraction quality
   - question-generation specificity
   - lexical ranking
   - blended weighting
   - local expansion

Do not guess blindly if the inspection pages can show the actual candidates.

## Recommended operating posture

For now:
- keep standard extraction as the production default
- keep OpenAI embeddings stable
- keep Groq on the cheap generative tasks
- keep question-generation guardrails conservative
- use document-scoped inspection heavily before making major retrieval changes
